# Подключение файлового хранилища через SFTP

## Результат

Локальный backend подключается к корпоративной PostgreSQL через существующий `DATABASE_URL`, а файлы читает и изменяет на сервере через `ssh2-sftp-client`, если `SFTP_ENABLED=true`.

Согласованное поведение:

- `SFTP_ENABLED=false` или отсутствует — файлы находятся в локальном `UPLOADS_DIR`.
- `SFTP_ENABLED=true` — загрузка, чтение и удаление файлов выполняются через SFTP.
- Адрес БД всегда определяется `DATABASE_URL`; его меняют вручную.
- Фронтенд продолжает использовать `/uploads/...`. Переключение требует перезапуска backend.

## Конфигурация

Добавить настройки в `.env.example`, конфигурацию приложения и валидацию:

```dotenv
# PostgreSQL: указать корпоративный сервер
DATABASE_URL=postgresql://user:password@db-server:5432/screen_hub?schema=public

# Файловое хранилище
SFTP_ENABLED=false
UPLOADS_DIR=uploads

SFTP_HOST=files-server
SFTP_PORT=22
SFTP_USERNAME=user
SFTP_PRIVATE_KEY_PATH=C:/Users/user/.ssh/id_ed25519
SFTP_PASSPHRASE=
SFTP_ROOT=/srv/screen-hub/uploads
SFTP_READY_TIMEOUT_MS=20000
```

- Флаг разбирать строго как `true` / `false`, без преобразования непустой строки в `true`.
- При включённом SFTP проверять обязательные параметры и доступность файла ключа. `SFTP_PASSPHRASE` необязателен.
- `SFTP_ROOT` — путь, видимый через SFTP; он может отличаться от пути на сервере при ограничении пользователя домашним каталогом.
- Ключ читать только на backend; секреты не выводить в логи.

## Изменения реализации

**Единый слой хранения**

- Добавить `StorageModule` с асинхронным интерфейсом записи, открытия потока чтения с метаданными и удаления файла.
- Реализовать локальный адаптер через `node:fs/promises` и удалённый через `ssh2-sftp-client`. Выбирать адаптер один раз при запуске.
- В `ProjectStorageService` и `VersionStorageService` сохранить проверку форматов и формирование относительных путей, заменив прямые операции с диском вызовами адаптера.
- Все вызывающие методы перевести на `await`, включая автоматическую загрузку версий из Figma.
- В БД сохранять относительные пути. Существующие записи и файлы должны оставаться доступными без миграции.

**Работа SFTP**

- Для первой реализации использовать отдельное соединение на файловую операцию, ограничив параллельность четырьмя соединениями. Закрывать соединение в `finally`; при чтении — после завершения или отмены потока.
- Создавать родительские каталоги перед записью; использовать обычные `put`/`get`, без `fastPut`/`fastGet`. Учитывать рекомендации библиотеки о конкурентных операциях и жизненном цикле клиента. [Документация ssh2-sftp-client](https://github.com/theophilusx/ssh2-sftp-client)
- Собирать серверные пути через POSIX-семантику независимо от локальной Windows. Запретить абсолютные входные пути, `..` и выход за корень хранилища, включая ссылки.
- При недоступности SFTP возвращать ошибку без переключения на локальную папку. Отсутствующий файл при удалении считать уже удалённым.

**Выдача файлов**

- При выключенном SFTP сохранить текущую раздачу через `@fastify/static`.
- При включённом SFTP зарегистрировать `GET` и `HEAD /uploads/*` вне API-префикса: получать метаданные и передавать файл потоком через backend.
- Сохранить MIME-тип и размер; отсутствующий файл возвращает `404`, недоступное хранилище — `503`. При отмене запроса закрывать поток и соединение.
- `PUBLIC_DIR`, сборка фронтенда и служебные локальные файлы остаются локальными.

**Согласованность файлов и БД**

- Новые загрузки записывать под уникальными именами внутри существующих каталогов проектов и версий, чтобы не перезаписывать используемый файл до успешного обновления БД.
- Сначала полностью сохранить файл, затем записать его путь в БД. При ошибке БД удалить только новый файл.
- Старый файл удалять после успешного обновления записи. Ошибку этой очистки логировать отдельно: она не должна запускать откат и удалять новый используемый файл.
- Схема Prisma и публичные DTO не меняются.

## Проверки и условия готовности

- Проверить оба режима: создание, просмотр, замена и удаление превью и версий; отдельно — автоматическую загрузку из Figma.
- Проверить `/uploads/` для существующих путей, MIME-типы, `HEAD`, отсутствующие файлы и отмену скачивания.
- Покрыть ошибки подключения, неверный ключ, отсутствие прав, обрыв передачи, ошибку БД после загрузки и ошибку удаления старого файла.
- Проверить защиту путей и параллельные запросы; убедиться, что SFTP-режим не записывает изображения в локальный `UPLOADS_DIR`.
- Выполнить сборку и тесты; интеграционные операции записи проверять в отдельном тестовом каталоге SFTP.
- Обновить README примером переключения и описанием настройки ключа.

Предполагается, что PostgreSQL доступна с локальной машины напрямую по сети или через уже настроенный VPN, а SFTP доступен по SSH-ключу. Создание SSH-туннеля, перенос существующих файлов и синхронизация локального и удалённого хранилищ в эту реализацию не входят.
