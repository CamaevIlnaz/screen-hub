# screen-hub — backend

## Backend сервиса просмотра дизайн-макетов
Backend предназначен для хранения, загрузки и предоставления дизайн-макетов и их версий для просмотра через frontend-приложение.

### Основные возможности

Сервис должен обеспечивать:
- хранение структуры дизайн-макетов;
- хранение нескольких версий одного макета;
- получение списка проектов, папок и экранов;
- просмотр текущей и предыдущих версий экранов;
- предоставление изображений и метаданных frontend-приложению;
- загрузку новых версий дизайн-макетов;
- автоматическую синхронизацию макетов с Figma;
- управление макетами через административную часть сервиса.

### Просмотр макетов

Пользователи могут просматривать опубликованные дизайн-макеты **без авторизации**.

Для публичного просмотра backend предоставляет API для получения:
- списка доступных проектов;
- структуры разделов проекта;
- списка экранов;
- текущей версии экрана;
- истории версий экрана;
- информации о версии;
- ссылок на изображения макетов.

### Структура данных

Основные сущности системы:
- **Проект** — отдельный набор дизайн-макетов;
- **Разделы** — используется для разных разделов внутри проекта;
- **Группа** — группировка по смыслу внутри раздела
- **Экран** — конкретный дизайн-макет (frame) из Figma;
- **Версия экрана** — сохранённое состояние экрана на определённый момент времени;
- **Админка** — Импорт / синхронизация, информация об операции загрузки макетов;
- **Пользователь** — администратор или пользователь с правами управления;

Один экран может содержать неограниченное количество версий.

### Загрузка дизайн-макетов

Новые версии могут загружаться двумя способами.

#### Ручная загрузка

Администратор через административную панель может:

- создать проект;
- создать или изменить структуру разделов;
- добавить новый раздел;
- загрузить новую версию существующего экрана;
- удалить или скрыть экран;
- удалить или скрыть отдельную версию;
- изменить название и порядок экранов.

При загрузке backend сохраняет файл изображения в файловое хранилище и записывает информацию о версии в базу данных.

### Автоматическая загрузка из Figma

Backend должен поддерживать автоматическую синхронизацию с Figma.

Для проекта сохраняются данные источника:

- идентификатор Figma-файла;
- список или структура импортируемых страниц/frames;
- параметры синхронизации;
- признак включённой автоматической загрузки.

Один раз в сутки запускается задача по расписанию (`cron`), которая:

1. получает актуальные данные из Figma;
2. определяет список доступных экранов;
3. получает изображения нужных frames;
4. сравнивает их с последней сохранённой версией;
5. создаёт новую версию только для изменившихся экранов;
6. добавляет новые экраны, если они появились в Figma;
7. фиксирует результат синхронизации.

Для сравнения версий может использоваться hash изображения или другой идентификатор содержимого. Это позволяет не создавать одинаковые версии при каждом ежедневном запуске.

### История синхронизаций

Для каждой операции импорта желательно сохранять:

- источник загрузки: `manual` или `figma`;
- дату и время запуска;
- дату окончания;
- статус;
- количество найденных экранов;
- количество добавленных экранов;
- количество обновлённых экранов;
- количество экранов без изменений;
- количество ошибок;
- текст ошибки или технический лог.

Пример статусов:

`pending` → `processing` → `completed`

или:

`pending` → `processing` → `failed`

Это позволит отображать историю загрузок в административной панели и проще диагностировать проблемы с Figma API.

### Работа с версиями

При появлении изменённого изображения backend создаёт новую версию существующего экрана.

Версия может содержать:

- идентификатор;
- идентификатор экрана;
- номер версии;
- источник создания;
- дату создания;
- ссылку или ключ файла;
- ширину и высоту изображения;
- размер файла;
- hash содержимого;
- идентификатор операции импорта;
- идентификатор пользователя, если загрузка была ручной.

Последняя актуальная версия может быть отдельно помечена как текущая.

### Хранение изображений

Сами изображения загружаются в отдельно от основной базы данных файловое хранилище на сервере в папку /uploads.

В PostgreSQL при этом хранится только ключ или путь к файлу и его метаданные.

Например:

`projects/{projectId}/screens/{screenId}/versions/{versionId}.svg`

При необходимости можно хранить:
- уменьшенное изображение для превью.

### Административная часть

Для административного API требуется авторизация.

Администратор должен иметь возможность:
- создавать и редактировать проекты;
- управлять разделам и группами;
- управлять экранами;
- загружать версии вручную;
- подключать Figma-файл;
- включать и отключать автоматическую синхронизацию;
- Настройки для токена Figma и настройка времени синхронизации.

На текущем этапе: NestJS + Fastify, PostgreSQL, Prisma, Swagger, пользователи и JWT-авторизация через httpOnly cookie.

## Быстрый старт

Требуется Node.js 20+.

### 1. Установка зависимостей

```bash
yarn install
```

### 2. Переменные окружения

```bash
cp .env.example .env
```

Задайте `JWT_SECRET` (обязателен).

### 3. PostgreSQL

```bash
yarn db:up
```

### 4. Миграции и Prisma Client

```bash
yarn prisma:migrate
```

### 5. Запуск backend

```bash
yarn start:dev
```
- Swagger: http://localhost:3000/docs

## Переменные окружения

См. `.env.example`:

- `PORT` — порт HTTP-сервера
- `API_PREFIX` — глобальный префикс API
- `SWAGGER_PATH` — путь к Swagger UI
- `DATABASE_URL` — строка подключения к PostgreSQL
- `POSTGRES_*` — параметры для Docker Compose
- `JWT_SECRET` — секрет подписи JWT (обязательный)
- `JWT_EXPIRES_IN` — срок жизни токена (например `7d`)
- `COOKIE_NAME` — имя auth-cookie (по умолчанию `access_token`)
- `CORS_ORIGIN` — origin фронтенда для CORS с credentials
- `UPLOADS_DIR` — каталог загрузок (по умолчанию `uploads`)
- `PUBLIC_DIR` — каталог собранного фронта (по умолчанию `public`)
- `PRISMA_SCHEMA_ENGINE_BINARY` — путь к бинарнику schema engine для серверов без доступа к CDN Prisma (см. ниже)

## Фронтенд в `public`

Собранный фронт (`web-screen-hub`) лежит в `public/` и раздаётся этим же backend с корня `/`: файлы отдаются как есть, остальные пути без расширения получают `index.html` (SPA-роутинг). `/api`, `/mockapi`, `/uploads` и Swagger работают как раньше. Если в `public/` нет `index.html`, раздача фронта отключена.

Пересобрать фронт (репозиторий `web-screen-hub` должен лежать рядом):

```bash
yarn build:web
```

Фронт собирается с пустым `VITE_API_BASE_URL`, поэтому запросы идут на тот же origin и CORS не нужен. На сервере достаточно развернуть только этот backend вместе с папкой `public/`.

## Сервер без доступа к CDN Prisma

Prisma Client работает через драйвер-адаптер `@prisma/adapter-pg` (`engineType = "client"`), поэтому нативный query engine не нужен. Но CLI Prisma перед `prisma generate` и `prisma migrate` всё равно скачивает **schema engine** с `binaries.prisma.sh` под платформу сервера (например `debian-openssl-3.0.x`). Если доступа к этому адресу нет, бинарник нужно положить на сервер вручную.

1. Определите target. Проще всего взять `linux-static-x64`: это статическая сборка, которой не нужен системный OpenSSL, и она подходит для любого x64 Linux, включая старые CentOS/RHEL с OpenSSL 1.0. Если нужен вариант под конкретный OpenSSL, посмотрите `openssl version`: для `3.x` — `debian-openssl-3.0.x`, для `1.1.x` — `debian-openssl-1.1.x` (или `rhel-openssl-1.1.x`), для `1.0.x` — `rhel-openssl-1.0.x`.

2. Скачайте бинарник на любой машине с интернетом. Хэш в ссылке соответствует Prisma `6.19.3`; после обновления `prisma` его нужно взять заново: `node -p "require('@prisma/engines-version').enginesVersion"`.

   Linux/macOS:

   ```bash
   curl -L -o schema-engine.gz https://binaries.prisma.sh/all_commits/c2990dca591cba766e3b7ef5d9e8a84796e47ab7/linux-static-x64/schema-engine.gz
   ```

   Windows (PowerShell, именно `curl.exe`):

   ```powershell
   curl.exe -L -o schema-engine.gz https://binaries.prisma.sh/all_commits/c2990dca591cba766e3b7ef5d9e8a84796e47ab7/linux-static-x64/schema-engine.gz
   ```

3. Скопируйте файл на сервер и распакуйте:

   ```bash
   scp schema-engine.gz user@server:/opt/prisma/
   # на сервере
   cd /opt/prisma
   gunzip schema-engine.gz
   chmod +x schema-engine
   ./schema-engine --version
   ```

   Ошибка про `libssl` при запуске означает, что не совпала версия OpenSSL — возьмите `linux-static-x64`.

4. Задайте переменную в окружении, где выполняются `yarn install`, `yarn build` и `yarn prisma:migrate:deploy` (shell, systemd, Docker):

   ```bash
   export PRISMA_SCHEMA_ENGINE_BINARY=/opt/prisma/schema-engine
   ```

С этой переменной `prisma generate` и `prisma migrate deploy` ничего не скачивают. При `yarn install` пакет `@prisma/engines` всё ещё пытается загрузить бинарники в `postinstall`, но ошибка там подавляется и установку не прерывает.

### Проверка и типичные ошибки

```bash
echo $PRISMA_SCHEMA_ENGINE_BINARY                            # путь к бинарнику, вывод не должен быть пустым
"$PRISMA_SCHEMA_ENGINE_BINARY" --version                     # schema-engine-cli <хэш>
node -p "require('@prisma/engines-version').enginesVersion"  # хэш должен совпадать
grep engineType prisma/schema.prisma                         # engineType = "client"
```

- **`Downloading Prisma engines for Node-API ...`** — CLI скачивает query engine, значит не видит `engineType = "client"`. Обновите код на сервере (`git pull`), затем `yarn install` и `yarn prisma:generate`.
- **`Downloading Prisma engines for <target>`** без «Node-API» — CLI не видит `PRISMA_SCHEMA_ENGINE_BINARY`. Задайте переменную в текущей сессии; после новой SSH-сессии она пропадает, поэтому лучше прописать её в `~/.bashrc`.
- **`export: ... недопустимый идентификатор`** — при `export` перед именем переменной не ставится `$`.
- **Ошибка про `libssl` при `--version`** — бинарник собран под другую версию OpenSSL, возьмите `linux-static-x64`.
- **`WebAssembly.Module(): invalid value type 'externref'`** — слишком старая Node.js. Нужна Node 20+ (Prisma 6 требует минимум 18.18, NestJS 11 — 20).

Чтобы увидеть, что именно CLI пытается скачать:

```bash
DEBUG="prisma:*" yarn prisma generate 2>&1 | grep -i "binaries to download"
```
